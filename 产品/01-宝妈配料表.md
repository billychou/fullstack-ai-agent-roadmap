# 配料表扫描小程序 · 产品全景文档

> 关联：代码库 `~/Src/health_scan` · 技术方案见该仓库 `docs/product-db-technical-design.md`
> 性质：写给自己的产品逻辑全景图，随产品演进持续更新（living doc）。

## 1. 一句话定位

**拍照扫配料表，AI 用大白话告诉你：这个食品，你家宝宝能不能吃、值不值得买。**

产品名：配料表扫描（仓库 health_scan）。形态：微信小程序 + FastAPI 后端 + 管理端。目标人群：母婴人群（宝妈/宝爸/长辈代购），个人/小团队 C 端产品，商业化方向正逐步验证。

解决的核心痛点：配料表上全是「植脂末、麦芽糊精、山梨酸钾」这种没人看得懂的名词，家长想知道的其实只有三件事——**有没有害、适不适合我家孩子、要不要买**。市面信息源（百科、科普号）讲概念不讲判定，且不会结合自家宝宝的月龄和过敏情况。

## 2. 产品的核心逻辑：两层判定模型

整个产品最重要的一条设计决策（也是后续一切功能的地基）：

**产品事实层（共享、缓存）× 个性化判定层（每人不同、零成本）**

- **事实层**：AI 以无偏好模式对配料表做一次基础分析——大白话配料翻译、健康评分、添加剂计数、糖警示、商品名、检出过敏原、建议最低月龄。结果按商品条码存入产品库，全网共享，每款商品全生命周期只跑一次 AI（180 天再验证）。
- **判定层**：确定性规则（`personalize.py`）把「用户偏好 + 宝宝月龄」叠加到基础分析上，产出最终购买建议（推荐/谨慎/避免）与个性化提示。不调 AI、可测试、可解释。
- **两条硬规则由代码强制执行而非依赖模型自觉**：过敏原交集 → 直接避免；月龄不足 → 直接避免。安全底线不交给大模型。

这条分层带来三个结构性收益：AI 成本从「每次扫描」降为「每款商品」（边际递减）；同款商品重复扫描秒回（<300ms），体验成为传播点；安全判定可靠性反而提升。

## 3. 用户与场景

核心用户画像：0-3 岁孩子的家长，妈妈为主，决策场景包括日常超市选购、母婴店比价、妈妈群种草后的验证、长辈代购时的把关。

高频场景（产品库命中率的来源）：同款奶粉/辅食/零食被同一个妈妈反复扫；妈妈群推荐某爆款后大家集中扫同一条码；断奶转奶期集中研究某几个品牌。这些场景决定了「按商品缓存」的命中率在母婴人群天然偏高（保守估计 70%）。

## 4. 功能地图与用户旅程

### 4.1 小程序端（3 tab + 结果页）

- **首页（扫描入口）**：拍照扫描（主按钮）、扫条码秒查、从相册选择、识别不清时手动输入配料表（弹层）。下方展示最近扫描。
- **结果页**：健康评分环（≥70 绿 / 40-69 橙 / <40 红）、购买建议（推荐/谨慎/避免）、配料大白话逐条翻译、糖警示、添加剂计数、个性化提示；命中产品库时展示「产品库 · 秒回」角标。
- **历史 tab**：按天分组的扫描记录，可回看任意一次的完整结果（浏览模式）。
- **我的 tab**：微信登录与资料（头像/昵称）、健康偏好设置、宝宝月龄。

### 4.2 偏好设置（个性化的输入）

| 偏好项 | 取值 | 规则层行为 |
|---|---|---|
| 过敏原 | 坚果/乳制品/大豆/麸质/海鲜/鸡蛋（多选） | 与检出过敏原交集非空 → 避免（硬规则） |
| 宝宝月龄 | 0/6/9/12/18/24/36 月龄（可选填） | 低于商品建议月龄 → 避免（硬规则） |
| 控糖 | 无/减少/避免 | 糖警示时收紧一档或提示 |
| 添加剂敏感 | 无/中/高 | 计数 ≥5（高）/≥8（中）时收紧或提示 |
| 热量关注 | 无/高 | 提示关注营养成分表热量 |

### 4.3 一次扫描的完整链路

1. 用户选入口：扫条码 → 查产品库；拍照/相册 → 前端 OCR（微信服务市场，失败降级手动输入）；手动输入 → 直接进分析。
2. 后端 analyze：条码命中且未超期 → 规则层个性化 → 秒回（source=product_db）；未命中 → AI 基础分析（偏好不进提示词）→ 入产品库 → 规则层 → 返回（source=ai）；纯条码未入库 → 404 引导拍照补录。
3. 用户保存记录：写 Scan + 产品库 scan_count 自增 + 补填商品图。
4. 埋点自动上报（analyze_done / analyze_404 / product_created / save_done），异常不影响业务。

### 4.4 管理端（Next.js + Ant Design）

看板/用户/扫描/产品/指标五个模块：用户管理（启用禁用）、扫描记录巡查、产品库运营（人工修正商品名）、运营指标报表。单管理员 env 账号 + JWT。

## 5. 运营与数据体系

埋点用自建 `events` 表（无外部 SDK），`scripts/metrics.py` 出日报：每日扫描/DAU、产品库命中率、AI vs 秒回耗时、404 补录转化率、D1 留存、热门商品 Top10。

**两条决策阈值（P3 观察期已定义，是后续路线的触发器）：**

- 产品库命中率 < 30% → 条码入口价值不足，优先做搜索/条码冷启动（接商品数据 API）。
- D1 留存 < 20% → 先做分享卡片、周报等回访钩子，再考虑导购。

## 6. 现状盘点（2026-08）

已完成：MVP 全链路（扫码/OCR/分析/历史/偏好）、登录与个人资料、产品库 P1-P3（后端规则层 + 前端扫条码/404 补录/秒回角标/月龄选择器，79 个测试通过）、埋点与报表、管理端、生产部署脚本（gunicorn + GitHub Actions SSH 部署）。

已治理的关键工程问题：AI 费用失控（前端超时重试 × LangGraph 递归）、外文配料死循环查询、共享账号静默降级、UTC 时间戳时差。这些教训已沉淀在个人记忆，此处只保留结论：**AI 链路必须有调用预算、结果缓存与并发合并；降级逻辑必须显式报错。**

已知短板（按对商业化的影响排序）：API 域名未备案（上线硬门槛）；OCR 计费在前端调用侧不可观测；配料文本经 URL 传参有截断隐患；商品名提取准确率待观察；数据合规（个人信息、B 端输出）未做正式审查。

## 7. 路线图（P3 之后）

按「数据阈值触发」而非「拍脑袋排期」推进：

| 阶段  | 功能                    | 触发条件/目的                         |
| --- | --------------------- | ------------------------------- |
| P4a | 分享卡片（结果页生成可转发图）       | D1 留存 < 20% 时的回访+拉新钩子           |
| P4b | 条码冷启动（淘宝/京东开放平台查品名预填） | 命中率 < 30% 时降低 404 补录摩擦          |
| P5  | 产品搜索 + 热门榜单           | 产品库数据资产的产品化（scan_count 已备好排序字段） |
| P6  | 电商导购（佣金）              | 留存与信任建立后的变现试探                   |
| P7  | B 端 API / 数据输出        | 需先完成个人信息与数据合规审查                 |

技术侧远期备选：qwen-vl 多模态后端一体化（省前端 OCR 按次计费）；营养成分表 OCR 数值化（热量规则 v2）。

## 8. 商业化逻辑（个人/小团队 C 端）

成本结构已从线性改为边际递减（AI 调用 = 扫描量 × (1−命中率)，命中率随库增长单调上升），这是小成本长跑的前提。变现路径按「先留存、再变现」：分享卡片拉新 → 搜索/榜单建立工具心智 → 导购佣金（CPS）为主、会员高级功能为辅。商业化前的硬前提：域名备案、微信 OCR 计费可观测、数据合规审查。

## 9. 维护约定

本文档是产品侧的单一事实来源（技术细节以 `health_scan/docs/product-db-technical-design.md` 为准）。大功能动手前先更新本文档的路线图与现状盘点；每次发版后核对第 6 节；决策阈值触发时在第 7 节标注实际数据。
