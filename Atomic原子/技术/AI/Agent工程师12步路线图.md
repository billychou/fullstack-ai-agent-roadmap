# 2026 年成为 Agent 工程师的 12 步路线图 —— Loops, Graphs, Evals, Context, Harness

> 原文：[AI Agent Engineer in 2026: 12 steps roadmap](https://threadnavigator.com/thread/2089393338977829278/)（Codez · @0xCodez · 2026-08-18）
> 转载：[WaytoAGI 飞书文档](https://waytoagi.feishu.cn/wiki/DlHIwfDqoiylXSktdSccaB0Gnwe)（摘要版，正文需登录）
> 本笔记基于原文完整推文串整理，七大支柱框架与 DSH（[[deepseek-harness学习指南]]）的架构思想高度呼应。

## 核心前提：七大支柱

决定 Agent 成败的是七大支柱：**Context（上下文）、Tools（工具）、Memory（记忆）、Loops（循环）、Graphs（图）、Harness（框架）、Evals（评估）**。作者的关键洞察：这不是七种独立技能，而是**同一种技能在七个维度上的投影**——

- 糟糕的上下文会破坏循环
- 没有评估的循环永远不会收敛到你能信任的东西上
- 没有评估的图会放大你的错误，而不是提升吞吐量
- 没有 Harness 的记忆会在会话结束时瞬间蒸发
- 没有上下文管理的工具会在工作开始前就让窗口过载

孤立地学习没有用，存在依赖顺序：**先打基础（Context/Tools/Memory），再执行（Loops/Graphs），最后可靠性（Harness/Evals）**。背景：前沿模型 SWE-bench Verified 一年内从 30% 提升到 80%+，但只有 17% 的高管表示已在公司全面采用 AI 智能体——差距就在这七根支柱上。

## 12 步详解

### 01. Context —— 读取真正加载的内容

Karpathy 的比喻：模型是 CPU，上下文窗口是 RAM，上下文工程是"用恰好下一步所需的内容填充 RAM"。

关键数字：Claude Code 中在你输入任何字符之前，约 **7,850 tokens** 已加载（系统提示、自动记忆、技能描述、CLAUDE.md、环境信息、MCP 工具名），而你的实际提示只有约 45 tokens——"Everyone optimizes the 45 and never opens the 7,850"。

实操：用 `/context` 查看分类明细，重点关注 memory files（过重说明 CLAUDE.md 超标）和 free space，配合 `/memory` 使用。

### 02. Context —— 先精简，再分层

Anthropic 为 Claude 5 一代删掉了 Claude Code 系统提示的 **80% 以上**，编码评测无损失。多数上下文是为更弱的模型写的指导，现在只浪费 token 并制造矛盾。

安全裁剪两条规则：

- **按块删除，不要逐行**——单句改动淹没在评测噪声之下。把绝对规则改写成原则，如"绝不写多行注释"→"写与周围代码风格一致的代码"
- 幸存内容放进**树形结构而非长卷**：CLAUDE.md 保持 **200 行以内**，只放模型无法从代码库推断的坑（如整数分计价、webhook 幂等、冻结目录）；其余变成 skill（描述启动时加载、主体调用时加载）或路径作用域规则

### 03. Tools & MCP —— 智能体能触及的范围

工具描述也是上下文。旧建议是用示例教工具，现在反了：示例会把模型锁死在示例的探索空间内，应设计**有表达力的参数**——一个 `pending | in_progress | completed` 枚举就能教完整生命周期，"the type is the documentation"。Anthropic 达到 SWE-bench SOTA 部分靠精修工具描述而非改模型。

- **延迟加载胜过倾倒**：Claude Code 只加载 MCP 工具名（约 120 tokens），按需取 schema；对工具描述做检索而非全量加载，选择准确率提升约 **3 倍**
- 描述写"何时适用"而不只是"做什么"——模型找不到的工具等于没发布

### 04. Memory —— 什么能在窗口之外存活

每个长任务最终会超出一个窗口，边界处的行为是设计决策，不要交给自动压缩去猜。具体机制（以 Claude Code 为例）：

- 项目根 CLAUDE.md 和自动记忆**从磁盘重新注入**（压缩后能回来）
- 路径作用域规则和嵌套 CLAUDE.md 存在消息历史里，被摘要后**不会回来**，直到再次读取匹配文件
- skill 主体上限**每个 5k、总计 25k**，最旧先丢、从尾部截断——关键内容放 SKILL.md **顶部**
- 最可靠的记忆是**写到文件**：计划文件、进度日志——存续于磁盘、不占窗口、能挺过压缩
- 主动压缩：`/compact focus on the auth bug`；下一任务不依赖前 20 条消息时大胆 `/clear`

### 05. Loops —— 何时停止

循环是 act → observe → decide → repeat，全部工程问题在最后一步：**它如何知道自己完成了？** 模型朝两个方向犯错：对半成品宣布胜利，或对早已完成的事无限打磨。两者都是结构性的，提示词救不了——**停止条件必须放在模型判断之外的代码里**。

- 有界工作：测试门或 schema 检查
- 未知规模探索：**loop-until-dry**——连续 K 轮没有新发现就停
- 关键细节：**对"所有见过的"去重，而不是对"已确认的"去重**——否则被否决的发现每轮重现，循环永不干涸（JS 实现用 `seen` Set + `dry` 计数器）

### 06. Loops —— 谁检查答案

收敛的循环仍然收敛于**模型自己相信的东西**。解法是 verifier——模型判断之外的、专职"试图杀死这个发现"的东西。三种模式：

- **对抗式验证**：每个发现派 N 个独立怀疑者去反驳，多数存活才保留
- **视角多元验证**：每个验证器一个镜头（正确性 / 安全 / 可复现）
- **评审团**：N 个并行尝试各自评分，从赢家综合并嫁接次优方案精华

验证器就是内联运行的 eval——写好验证器的团队做第 11 步会容易得多。

### 07. Graphs —— 什么并行运行

节点是工作单元，边意味着"这个输出喂给那个输入"。**没有数据跨越就没有边**，等待就是纯浪费。主力形态是**菱形**：扇出取广度 → 普通代码做归约（flatMap + Set，不是 agent）→ 一个 agent 综合。"边是免费的，把 agent 花在判断上，不是管道上。"

上限很高：Claude Code 动态工作流可协调**最多 1,000 个并行子 agent**，编排零模型 token（脚本是脚本不是对话）。该架构曾支持一个团队六天把约 **96 万行 Bun 运行时从 Zig 移植到 Rust**，测试 99.8% 通过。

### 08. Graphs —— 拓扑的代价

两个选择决定大部分延迟和开销：

- **parallel() vs pipeline()**：parallel 屏障让所有节点等最慢者；pipeline 让每个条目独立流过所有阶段。默认 pipeline，只有某阶段真需要全部前置结果（如跨集合去重）才用屏障
- **按节点分层模型**：子 agent 默认继承会话模型，大任务全部按顶级模型计费。有界重复节点（提取字段、分类工单）用便宜模型，只有合并/综合节点保持高档——100 个便宜扇出节点喂一个顶级综合，成本远低于全部平铺

### 09. Harness —— 在会话死亡中幸存

Anthropic 的框架：长任务是**一个由轮班工程师组成的软件项目，每个新工程师对上一班毫无记忆**。单靠压缩解决不了。两类可复现失败：agent 试图一次性做完整个应用（上下文中途耗尽，给下个会话留半成品）；后期看到真实进展就宣布完工。

解法是先跑一次 **initializer agent** 搭环境：init.sh 启动开发服务器、进度日志、初始 git commit，以及一个 **JSON 格式的功能清单**（claude.ai 克隆项目超 200 条，全部标记 failing）。Agent 只能把 `passes` 翻成 true，措辞刻意强硬："It is unacceptable to remove or edit tests"——能改规格的模型就会改规格。选 JSON 而非 Markdown，因为模型不当改写 JSON 的概率可测量地更低。

### 10. Harness —— 每会话一个增量

环境搭好后，每个编码会话的契约：**定位 → 恰好选一个功能 → 像用户一样验证 → 留下干净的仓库**。定位仪式是机械的：pwd → 读进度文件 → 读 git log → 读功能清单 → 跑 init.sh → **动手前先确认基础功能仍然正常**。

给它**真实的测试工具、要求像人类用户一样验证**（浏览器自动化、真实点击）——这一条在 Anthropic 实验中显著提升表现，能抓到纯看代码看不见的 bug。

### 11. Evals —— 要数字，不要感觉

崩溃点总是同一句话：用户说改版后 agent 变差了，团队除了猜和试没有任何验证手段。

- 起步很小：**20–50 个来自真实失败的任务**就很好（早期改动效应量大），从手工测试、bug tracker、客服队列取材
- 任务要写得让**两位领域专家独立得出相同结论**——任务里的歧义会变成指标里的噪声
- 构建平衡集合：该触发的场景和不该触发的都要测
- 三种评分器搭配：**代码类**（快、便宜、客观，能用就用）、**模型类**（评分细则校准人类，最好每维度一个独立 judge）、**人类**（金标准，少量用于校准前两者）
- **评产出物而非路径**：检查精确工具调用序列很脆弱，agent 常会找到你没预料的有效方案

### 12. Evals —— 让数字保持诚实

**不看 transcript 就不知道评分器是否工作**：任务失败时要能区分是 agent 真错了，还是评分器拒绝了有效方案。两个陷阱：

- 多次试验 **0% 通过率通常意味着任务写坏了，不是 agent 不行**。Opus 4.5 在 CORE-Bench 起初 42%，研究者发现死板评分（期望 96.124991… 却拒绝 96.12）、含糊规格、不可复现任务，修复后达 **95%**
- 相反陷阱是**饱和**：100% 的 eval 只能防回归，没有可爬的坡

区分两个指标：**pass@k**（k 次至少一次成功的概率，随 k 上升）；**pass^k**（k 次全成功的概率，快速下降——单次 75% 时三次全过仅约 42%）。一次成功即够的用 pass@k，**面向用户的用 pass^k**。最后接入 CI：新模型发布从几周手工测试变成"跑套件、读 diff 的一天"。

## 附：每支柱一个 Claude 实操任务（7 jobs）

1. 用 `/context` 和 `/doctor` 测量你的上下文构成
2. 给每个 MCP 工具描述加一句 "use when"
3. 把状态移到文件系统的 plan.md
4. 给循环加三方验证器
5. 把线性循环任务改成扇出 + 合并
6. 让 Claude 当 initializer agent：生成 init.sh、进度文件、全 false 的 JSON 功能清单
7. 把上周的 bug 转成 20 个带明确通过标准的 eval 任务

## 结论

模型自己在变好，这是免费的。**不免费的是模型周围的系统**：精简的上下文、可被选中的工具、能挺过窗口的记忆、会收敛并被核查的循环、扇出而非排队的图、让下一班接续上一班的 harness、以及一个告诉你有没有变好的数字。

> "The ones who build the twelve steps will ship agents that work on days the model is having a bad one."
