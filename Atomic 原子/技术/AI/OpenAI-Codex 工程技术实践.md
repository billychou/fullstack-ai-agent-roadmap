# OpenAI 工程技术：在智能体优先的世界中利用 Codex

> 原文链接：[Harness Engineering: Leveraging Codex in an agent-first world](https://openai.com/zh-Hans-CN/index/harness-engineering/)
> 作者：Ryan Lopopolo（OpenAI 技术人员）
> 发布日期：2026-02-11
> 核心案例：一个 3 人团队用 5 个月交付约 100 万行代码的产品，**没有一行代码是人工编写的**——全部由 Codex 智能体完成。

## 核心前提

**人类掌舵，智能体执行。** 工程师的主要工作不再是编写代码，而是设计环境、明确意图和构建反馈回路，使 Codex 智能体能够可靠地工作。

关键数据：
- 3 名工程师，5 个月，约 100 万行代码
- 1,500 个 PR 被打开与合并
- 平均每位工程师每天处理 3.5 个 PR
- 团队扩展到 7 人后，吞吐量反而增加
- 产品已有数百名内测用户（含高级用户）

---

## 一、重新定义工程师的角色

### 深度优先工作方式

将更大目标拆解为更小的构建模块（设计、代码、评审、测试等），提示智能体构建这些模块，再用它们解锁更复杂的任务。

当事情不顺利时，解决方案不再是"再努力一点"，而是追问：**"究竟还需要什么样的能力，我们又该如何让这个能力对智能体来说既清晰可读又可强制执行？"**

### 人类几乎完全通过提示与系统交互

- 工程师描述任务 → 运行智能体 → 允许其打开 PR
- Codex 直接使用标准开发工具（gh、本地脚本、嵌入代码仓库的技能）收集情境
- 人类可以审核 PR，但并非必须——**几乎所有审核工作已调整为智能体对智能体**

---

## 二、提高应用程序的可读性

### 让应用对智能体直接可读

**启动与调试**：
- 应用可根据 git worktree 启动，Codex 可为每次更改启动并驱动一个实例
- Chrome DevTools 协议接入智能体运行时：DOM 快照、屏幕截图、导航技能
- Codex 能复现错误、验证修复、直接推理 UI 行为

**可观测性**：
- 日志、指标、追踪通过本地可观测性堆栈展示给 Codex（临时、随工作树销毁）
- Codex 使用 LogQL 查询日志、PromQL 查询指标
- 单次 Codex 运行可在单个任务上持续工作**超过 6 小时**（通常在人类睡眠时间）

## 三、将代码仓库设为记录系统

### 核心经验：给 Codex 的是一张地图，而不是一本 1,000 页的说明书

**失败的尝试**：一个大型 AGENTS.md——情境是稀缺资源，巨大指令文件会挤掉任务、代码和相关文档。当一切都"重要"时，一切都不重要了。

**成功方案**：AGENTS.md 作为**内容目录**（约 100 行），代码仓库的知识库位于结构化 `docs/` 目录：

```
AGENTS.md
ARCHITECTURE.md
docs/
├── design-docs/          # 设计文档（含验证状态 + 核心理念）
│   ├── index.md
│   ├── core-beliefs.md
│   ── ...
├── exec-plans/           # 执行计划（一流工件）
│   ├── active/
│   ├── completed/
│   ── tech-debt-tracker.md
├── generated/            # 自动生成（如 db-schema.md）
│   └── db-schema.md
├── product-specs/        # 产品规格
│   ├── index.md
│   ── new-user-onboarding.md
├── references/           # 外部参考（格式化为 LLM 可读）
│   ├── design-system-reference-llms.txt
│   ├── nixpacks-llms.txt
│   └── uv-llms.txt
├── DESIGN.md
├── FRONTEND.md
├── PLANS.md
├── PRODUCT_SENSE.md
├── QUALITY_SCORE.md
├── RELIABILITY.md
└── SECURITY.md
```

**关键机制**：
- **渐进式披露**：智能体从小而稳定的切入点开始，被指导下一步去哪查看
- **专职 linter + CI 作业**：验证知识库更新状况、交叉链接、结构正确
- **doc-gardening 智能体**：定期扫描过时文档，发起修复 PR

## 四、目标是智能体的可读性

### 核心洞察

从智能体角度来看，**它在运行时无法在情境中访问的任何内容都是不存在的**。存储在 Google Docs、聊天记录或人们头脑中的知识都无法被系统访问。

**推论**：代码仓库本地的、已版本化的工件（代码、Markdown、模式、可执行计划）就是它所能看到的全部。

### 实践含义

- 那次让团队在架构模式上达成一致的 Slack 讨论？如果智能体无法发现它，就像迟了三个月入职的新员工一样对其一无所知
- 为 Codex 提供更多情境 = 组织和展示正确信息，而非用临时指令使其不堪重负
- 就像为新队友提供引导（产品原则、工程规范、团队文化），将这些信息提供给智能体会带来更一致的输出

### 技术选择偏好

- 倾向选择可完全内化于仓库推理的依赖项和抽象
- **"枯燥"的技术**（可组合性、API 稳定性、训练集表现好）往往更容易建立模型
- 有时让智能体重新实现部分功能子集比绕过公共库中不透明的上游行为更便宜
  - 示例：不用通用的 p-limit 包，而是自建带并发的 map 辅助函数——与 OpenTelemetry 仪表紧密集成、100% 测试覆盖率、行为完全符合运行时预期

## 五、规范架构与品味

### 核心原则：强制执行不变量，而非对实施过程进行微观管理

**严格架构模型**：每个业务域划分为一组固定的层，依赖方向经过严格验证，仅允许有限的一组边。

```
业务域内（如应用设置）的代码只能"向前"依赖：
Types → Config → Repo → Service → Runtime → UI

横切关注点（认证、连接器、遥测、功能标志）通过单一显式接口进入：Providers
其他任何内容都不被允许，并通过自动化方式强制执行
```

**执行机制**：
- 自定义 linter（由 Codex 生成）
- 结构测试
- 错误信息中注入修复指令（在智能体情境中）

**"品味不变式"示例**：
- 结构化日志记录
- 模式和类型的命名约定
- 文件大小限制
- 特定平台的可靠性要求

**关键取舍**：
- 在中央层面强制执行边界，在本地层面允许自主权
- 生成的代码不总是符合人类风格偏好——只要输出正确、可维护、对未来的智能体运行清晰易读，就算达标
- 人类品味通过审查评论、重构 PR、面向用户的 Bug 反馈到系统——记录为文档更新或直接编码到工具中

## 六、吞吐量改变了合并的理念

### 核心变化

在智能体吞吐量远超人类注意力的系统中：**纠错成本低，而等待成本高**。

**实践调整**：
- PR 生命周期很短
- 测试偶发失败通常通过后续重跑解决，而非无限期阻碍进展
- 尽量减少阻塞合并门

**对比**：在低吞吐量环境中，这样做是不负责任的；在这里，这通常是正确的选择。

## 七、"智能体生成"实际上意味着什么

**整个代码库**都是智能体的产出，包括：
- 产品代码与测试
- CI 配置和发布工具
- 内部开发者工具
- 文档和设计历史
- 评估框架
- 审阅评论和回复
- 管理代码仓库本身的脚本
- 生产仪表板定义文件

**人类始终参与**，但工作抽象层次不同：优先处理工作、将用户反馈转化为验收标准、对结果进行验证。当智能体遇到困难时，视为信号——识别缺失的内容（工具、指导与约束、文档）并反馈到代码仓库中，**始终由 Codex 自己编写修复**。

## 八、不断提高的自主水平

### 端到端驱动新功能的完整流程

给定一个提示，Codex 现在可以：
1. 验证代码库的当前状态
2. 重现已报告的漏洞
3. 录制一个演示故障的视频
4. 实施修复措施
5. 通过运行应用程序来验证修复
6. 录制第二个视频，演示解决方案
7. 打开 Pull Request
8. 回应智能体和人类反馈
9. 检测并修复构建故障
10. **仅在需要判断时才交由人工处理**
11. 合并更改

**注意**：此行为很大程度上取决于此代码仓库的具体结构和工具，不应在没有类似投入的情况下假定它可以泛化。

## 九、熵与垃圾收集

### 问题

完全自主的智能体会复现代码仓库中已存在的模式——包括不均衡或不够理想的模式。随着时间推移，不可避免地导致漂移。

### 解决方案：将"黄金原则"编码到代码仓库 + 循环清理流程

**黄金原则示例**：
1. 倾向于使用共享的实用程序包，而非手工编写的辅助工具——将不变式集中管理
2. 不使用"YOLO 式"探测数据——验证边界，或依赖类型化的 SDK，这样智能体就不会意外地基于猜测的结构进行构建

**后台清理流程**：
- 定期运行一组后台 Codex 任务
- 扫描偏差、更新质量等级、发起有针对性的重构 PR
- 大多数 PR 可在一分钟内完成审查并自动合并
- **功能类似于垃圾回收**

**类比**：技术债务就像一笔高息贷款——不断地以小额贷款的方式偿还债务，总比让债务不断累积再痛苦地一次解决要好。

## 十、我们仍在学习的内容

### 已知有效

- 这一策略在 OpenAI 的内部发布和采纳过程中表现良好
- 为真实用户打造真实产品，帮助将投资锚定在现实中，引导实现长期的可维护性

### 未知领域

- 在一个完全由智能体生成的系统中，**架构连贯性会如何随着时间的推移而演变**
- 人类的判断力在哪些方面能发挥最大作用，以及如何对这种判断力进行编码使其发挥更大作用
- 随着模型功能不断增强，这一系统将如何演变

### 核心洞察

> 构建软件仍然需要纪律，但纪律更多地体现在**支撑结构**上，而不是代码上。保持代码库一致性的工具、抽象和反馈回路变得越发重要。

当前最棘手的挑战集中在：设计环境、反馈回路和控制系统，帮助智能体实现目标——大规模构建和维护复杂、可靠的软件。

## 与 DSH / 本库笔记的关联

- [[deepseek-harness学习指南]] —— OpenAI 的 Codex 与 DeepSeek Harness 是同一范式的不同实现：都强调"一切皆插件"、AGENTS.md 作为入口、事件溯源/会话日志。但 Codex 更偏向"闭源成品 + 深度集成 OpenAI 模型"，DSH 更偏向"开源底座 + 模型无关"
- [[Agent工程师 12 步路线图]] —— 本文是"Harness 支柱"的顶级实战案例：跨会话接力（initializer agent 的变体）、JSON 功能清单（防规格篡改）、每会话一个增量、Evals 评测体系（质量等级追踪）
- [[06-工程化与 LangSmith]] —— 可观测性工具对智能体可读（LogQL/PromQL 查询）、CI 集成、反馈回路设计

### 关键差异点（Codex vs DSH）

| 维度 | OpenAI Codex（本文） | DeepSeek Harness |
|---|---|---|
| 模型绑定 | 深度绑定 OpenAI 模型（GPT-5） | 约 40 家厂商，多模型一等公民 |
| 开源 | 核心闭源 | MIT 开源 |
| 扩展机制 | Hooks / Skill / MCP（只能叠加） | 一切皆插件，任意组件可替换 |
| 架构强制 | 自定义 linter + 结构测试 | Cordis 插件内核 + Patch 机制 |
| 会话模型 | 隐式（PR 驱动） | 显式事件溯源（SessionEvent 日志） |
| 适用场景 | 企业团队、复杂审批 | 成本敏感、二次开发、白标定制 |

### 可借鉴的实践（与 Harness 无关，通用）

1. **AGENTS.md 作为目录而非百科全书**（约 100 行）
2. **docs/ 结构化知识库 + 专职 linter 验证新鲜度**
3. **doc-gardening 智能体**定期清理过时文档
4. **黄金原则编码 + 后台垃圾回收式重构**
5. **让应用对智能体可读**（git worktree 启动、DevTools 协议接入、可观测性堆栈）
6. **吞吐量改变合并理念**：纠错成本低时，等待成本更高
